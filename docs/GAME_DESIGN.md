# 灰烬地城：从规则验收场到完整游戏的设计合同

日期：2026-09-24（UTC+8）。设计版本：v0.2。
状态：本次完成的是设计收敛，以下玩法与表现为实施要求，不是已经交付的功能。
复核基线：灰烬地城 `11fe121` / 0.1.0a1，内核 `422fc56` / 0.13.1。

文档优先级：本文件定义目标游戏和分层原则；ROADMAP 定义交付顺序；RULES_SCOPE 与 VALIDATION 继续描述已实现的 M1。设计稿不得覆盖实测记录，也不得让 README 声称完整游戏已经可玩。

## 1. 产品判断

世界二次开发是正常用法，不是底座失败。底座不是让任意世界零代码自动长出来的游戏生成器。灰烬地城应有自己的规则代码、内容、状态投影、敌人决策和表现适配器；必要时也可以改进真正通用的基础设施。

验收标准不是“内核一行未改”，而是：世界专用规则留在世界中；通用能力有清楚合同；一个新世界不需要重造鉴权、事务、回执、事件保留和断线恢复。

M1 的 83 项测试证明有限场景的规则/传输行为，不证明游戏循环成立。继续横向追加三个职业的攻击按钮，会扩大规则实验室，不能替代真正冒险。

## 2. 三层责任与可接受的二次开发

| 层 | 应承担 | 不应承担 |
|---|---|---|
| 通用内核 | 身份与权限、按世界挂接状态、函数注册/发现/校验/调用、事务、版本迁移、操作回执、事务随机数、事件/视图、持久定时器 | D&D 等级、HP、先攻、背包槽、任务奖励、特定地图、怪物智力 |
| 可选开发工具/客户端基础 | 传输组合示例、带权限的快照与流同步、去重/历史恢复、表现事件封装、资源引用校验、可复现示例和验收工具 | 万能渲染器、完整 RPG 框架、自动为所有世界选动画、第二个服务端 AI |
| 世界包与世界前端 | SRD 规则、成长/职业、战役/地图/敌人/奖励、可见性、脚本 NPC、战斗推进、语义事件到资源的绑定、角色面板与交互 | 复制一套 token 系统、绕过内核直接改数据库、自己另算权威骰点或伤害 |

先在灰烬地城实现具体用法；遇到对其他世界同样必要的能力缺口，再以无 RPG 术语的最小接口补到底座或可选工具包。无需等两个例子一模一样才允许修通用缺陷，但不为了一个法术建通用规则语言。

## 3. 从代码确认的差距

| M1 现状 | 对完整游戏的影响 | 下一步归属 |
|---|---|---|
| 一个 `encounter/state`，固定两个 seat；`_finish` 按剩余未失能个体数量结束 | 不等于多成员阵营胜败，无法表达多场战斗后的战役状态 | 世界战役/遭遇分离；按阵营、目标和失败条件裁决 |
| 必须两个身份占满双方席位才能开始 | 单个用户不能独立冒险；敌人还需要另找用户操作 | 世界脚本敌人策略；一个用户可玩，合作模式另外验收 |
| 固定 NPC 配置，没有职业、经验、装备或任务结果 | 测试完就结束，无成长和长期目标 | 持久角色扩展、内容与奖励账本 |
| `watch.js` 重建网格、更新文本，每轮重读近期事件 | 能看当前数值，但没有动作过程、因果播放和资源绑定 | 世界表现适配器 + 复用已有同步/去重基础 |
| 当前 battle 投影公开全部敌人数值；bootstrap 暴露整个实验状态 | 不适合隐藏房间、陷阱与个人奖励 | 授权视图、按观察者投影与私人事件路径 |
| 两席位的路径暂停只处理机会攻击 | 增加法术后不能将一切反应都当成“伤害已扣完再补动画” | 世界内明确的待决阶段/继续点；逐项覆盖法术反应 |

M1 保留为规则回归夹具。不通过不断添加 `if actor == warden`、再添加第三个 seat 的方式把它养成战役系统。

## 4. 真正要交付的游戏

原创序章暂名：**灰烬地城：失落火种**。玩家进入废弃墓库，调查火种去向，选择路线和风险，带回或处置火种。核心目标不是刷同一骷髅，而是带着持续存在的角色完成一段有代价、有选择、有结果的冒险。

游戏循环：

`营地接取目标 → 准备装备 → 进入区域 → 探索/交涉/避险/战斗 → 结算战利品与经验 → 决定继续或撤退 → 回营恢复/升级 → 用新能力进入下一段 → 终局`

最小可玩切片先做六个区域：营地、门厅、岔路、可绕开的风险房、守卫房、可返回的补给点。它必须包含一种非战斗解决方式、一次真正的资源取舍、一次可见升级，以及升级后能实际使用的新能力。六个区域不是六个按顺序播放的按钮或固定脚本。

完整序章再扩至约 8–12 区域和多个结果；“火种带回、留在原地、冒险失败”的具体条件与任务状态写入世界，不由最终自然语言自行宣布。计时目标只衡量有效决策/战斗回合，不承诺一个固定的真实分钟数能覆盖所有 Agent 延迟。

### 人数与敌人

第一条完整可玩链路以单用户、一个受控 PC 为验收对象，使用专门编排的单人遭遇。选择先闭合 Fighter 的 1→2 级流程是实施顺序，不是删除 Rogue/Wizard 的目标。

完整序章提供 Fighter、Rogue、Wizard 三种可审计构筑路径。合作模式按 1–3 个独立身份加入各自角色，单人与合作分别验收，不用同一组怪物数量假装自动适配。每个用户只控制被授权的角色，不借测试工具替其他人的角色作决定。

敌人与剧情 NPC 由世界作者编写的确定性策略驱动，不调用服务端大模型。策略只能读取其获准感知，走同一套行动预算、路径、攻击和反应裁决；不能绕过规则扣血，也不能假装成外部 Agent。敌人有简单且明确的目标、目标选择、撤退/投降条件和反应选择，而不是只能站着挨打。

脚本敌人的服务器执行入口只获准操作世界管理的 NPC；不能伪造用户令牌或代理离线用户。一次推进运行到下一个需要真实用户决定的节点便停止，采用有限步骤预算，防止 NPC 自动循环无界消耗。

## 5. 成长曲线是玩法变化，不只多一根经验条

原先三个固定 3 级角色保留作高级规则夹具和构筑终点；面向玩家的序章修订为 **1→3 级的成长路径**。这是本轮设计调整，尚未实现。后续 3→5 级属于内容扩展，不在第一完整切片中一次做完。

| 阶段 | 玩家要学会/获得什么 | 反馈与验收 |
|---|---|---|
| 1 级：生存与认识世界 | 核心动作、距离、资源、可绕过风险，第一次装备/消耗品选择 | 玩家能理解为何命中/失败，受伤与消耗能改变下一步决策 |
| 2 级：可用策略变多 | 对应职业的真实新增能力与资源，使用同一持久角色完成升级 | 升级前后角色表、可用能力、资源上限与按钮说明一致；随后必须有使用新能力的挑战 |
| 3 级：形成职业方向 | 合法子职业及相关新机制，处理组合风险和最终目标 | 不是只修改等级数字；所有新能力已有规则闭包和表现反馈 |

SRD 5.2.1 第 23 页的经验门槛为 1 级 0、2 级 300、3 级 900。职业特性、生命值与熟练变更按所选构筑和规则逐项计算，不发明统一“每级攻击+10%”。本序章采用固定生命值增长选项，记录来源与选择，避免升级重复请求重掷获利。

经验奖励分清两类：怪物/遭遇经验参考实际 SRD 数据；探索和目标经验属于作者/GM 预先定义的奖励政策，必须显式标明，不冒充规则书规定的统一数值。不得把“遭遇设计的 XP 预算”直接当作玩家每人的经验收入，也不得多种解决路径重复领奖。

先定义每条必经/可选路线的经验上下界和奖励来源，再模拟验证能否按设计到达升级节点；此文不把未经测试的奖励分配表描述成已平衡。若要将升级安排在叙事安全点，应安排奖励授予点，而不是经验已达门槛后擅自要求必须睡觉才能升级。

升级时一次性保存属性、职业特性、资源上限、可选项和版本；新能力暂未实现就不开放相应构筑。获得等级不额外隐含“满血、所有法术位恢复”的私有加成。升级选择未完成时明确显示待选择状态，不能显示成功而底层还在使用旧能力。

### 另外两条成长线

装备与补给提供横向选择：可使用的武器/护甲、药水、任务钥匙和探索工具，而不是无来源的词条膨胀。装备实际生效必须遵守熟练、占手、穿脱、消耗和已实现的相关规则。

世界进展提供长期反馈：捷径开启、房间已探索、NPC态度/任务分支变化、目标已处理。它们可以是本世界扩展状态，但不自动变成所有世界通用的好感度/声望字段。

### 难度节奏

按当前角色、人数和可用资源安排低风险、资源消耗、抉择和高潮，不只给敌人加 HP。用 SRD 第 202–203 页的遭遇预算作为起点，再测单人脆弱性、行动数量、地形与先攻波动；数值预算不是胜率保证。首版不暗中调骰、不动态篡改 AC/伤害来救场。

## 6. 世界状态要支持“战斗之外还活着”

以下是世界数据责任，不是新建微服务或统一内核字段：

| 状态 | 生存周期与职责 |
|---|---|
| 战役/冒险进度 | 跨遭遇持续：当前区域、任务阶段、世界时间、已完成目标、内容/存档版本 |
| 本世界角色扩展 | 绑定稳定 role_id：构筑、等级、经验、资源、背包、装备、永久选择；不能用战斗 seat 代替角色 |
| 队伍与参与权限 | 成员、就绪、队伍目标；加入必须授权；脱线不转移控制权 |
| 遭遇 | 当前参战实体、阵营、先攻、轮次/回合、动作预算、状态持续期、待决反应 |
| 世界对象 | 房间、门、容器、陷阱、交互条件；已经处理的对象刷新后不会自动重新生成奖励 |
| 奖励/战利品领取记录 | 持久来源 ID、接收者、已授予内容；不能仅依赖会过期的事件流 |

全局角色档案与世界挂接数据分开。跨世界稳定角色是产品方向；M1 的 universe 绑定凭据是当前实现边界，不将其改写成最终“角色永远只能属于一个世界”的原则。本轮游戏实施不借此引入新的联合登录系统，缺口留在底座评审中。

奖励必须防止两个不同 operation_id 反复领取同一个来源，不能只依赖网络重试幂等。队伍领奖/掉落分配明确受益者与资格；同一容器被多人打开、重复结算、刷新或换客户端不能复制物品。领奖标记、经验/物品变化和对应事件在一次世界事务中提交。

## 7. 战斗、休息、失败与时间

普通动作、附赠动作、反应与免费选择各有自己的合法性条件。法术和职业能力通过世界内的具体处理器组合，不为所有规则发明万能 Effect DSL。待决攻击与待决反应需要明确阶段和继续点；例如加入改变当前命中结果的反应时，不能先提交最终伤害再倒扣。

死亡、失能、稳定、撤退和投降不能一律视为删除实体；多人战斗不能沿用 M1 “只剩一个未失能者就结束”的条件。按阵营和遭遇目标判断终局，保留濒死处理、救助与失败结果。新游戏或读档操作要明确，不暗中替玩家复活或重新生成身份。

三个时钟分开：世界内虚构时间（探索/休息）、战斗回合规则时机（本人回合开始/结束/特定触发）、前端表现时间（毫秒）。不能用现实网络等待触发休息恢复，也不能要求用户等真实八小时才读完长休。时间跳跃由世界裁决，处理该段时间内的已定义事件与中断；多人世界不能让一人睡觉就跳过另一个正在进行的战斗。

对 M1 的用户角色不设置掉线自动放弃反应。脚本 NPC 可以依策略即时决定，不等一个根本不存在的客户端。休息按有效前置条件、资源恢复与中断规则处理，不能靠反复点按钮无成本恢复。

## 8. 没有素材，也必须先把“表演数据”做成立

当前 SVG 观察器只是数值调试视图，不算表现层已完成。目标是先用几何占位资源证明动作顺序、位置、目标、效果与恢复正确，再让正式素材绑定同一份语义数据。

**快照回答现在是什么；已提交事件回答刚刚发生了什么；前端决定怎么表现。** 不能靠比较前后 HP 猜测谁攻击了谁，不能从客户端播放结束推导伤害或动作完成。

继续使用现有 `PresentationCue` 的 `version/cue_id/subject_id/channel/phase/name/data` 和已有事件流；不增设一套平行传输或把新字段直接塞进旧信封。世界专用字段放在已允许的 data 中，世界自己校验它的 schema。现有 phase 只有 start/finish/cancel；反应暂停/恢复可用明确命名的子事件表达，不伪造内核已支持别的 phase。

### 所有表现事件必须能回答

- 哪个场景、哪个实体、什么来源（用户 Agent、玩家、脚本 NPC、系统规则）？
- 对应哪个根操作/持续行动、哪一个因果步骤？目标是谁，哪些事实已裁定？
- 是受理、等待反应、已结算、取消还是失败？失败不能播放命中。
- 移动发生在哪一段已接受路径？哪些位置尚未到达？
- 哪个数值/状态真正变了，前值、后值、原因与可见范围是什么？
- 当前记录适合现场短暂播放，还是只作为历史显示？

这些数据是未来 contract 的世界 payload，不宣称 M1 已经返回。事件唯一性复用内核 event_id；单个动作的多个语义步骤使用稳定 cue ID、因果引用和步骤次序。跨流不能拿墙钟时间排序冒充全局因果顺序。先采用同一获准有序场景流；确需跨流联动时补足显式因果关联，并验收旧客户端行为。

### 具体的表现闭环

| 行为/结果 | 权威事实 | 无素材占位表现 | 后续资源绑定 |
|---|---|---|---|
| 移动 | 起点、已执行路径段、终点或暂停位置 | 圆点沿路径移动、朝向改变、反应位置停下 | walk/run、朝向与足步资源 |
| 攻击未命中/命中/重击 | 攻击者、目标、骰点结果、实际伤害与 HP 变化 | 前摇标记、挥动线、miss/伤害飘字、血条、受击/倒地 | attack、impact、hit/death，重击变体 |
| 施法/反应打断 | 待决触发、目标/范围、消耗、最终效果 | 施法圈、投射线或范围遮罩、护盾/中断标记 | cast/projectile/area/shield，可缺省纹理 |
| 状态变化 | 来源、开始/结束原因与有效时机 | 图标、轮廓和文字说明；正确清除 | 状态图标、持续粒子、姿态 |
| 掉落与拾取 | 容器/物品实体、已领取者、背包变化 | 地面标记、拾取轨迹、背包格变化 | 宝箱/掉落/拾取模型与音效 |
| 经验与升级 | 奖励来源、经验前后值、等级/能力变更 | 经验条变化、升级提示、明确的新能力说明 | UI 动效、图标和升级特效 |
| 对话/任务/门 | 明确的发言来源、目标阶段、门状态 | 气泡、日志、任务提示、门开闭 | 字体/音效、人物待机与交互动画 |

动画可以先平滑展示最终已确认的结果；不得用动画延迟来阻止或重写服务器下一回合。现场事件可排队但必须有时长/数量界限；积压太旧时吸附当前状态、保留历史标记，不回放十分钟前的挥剑并再次弹领奖动画。

### 合成数据例：一次已经裁决的命中

下面只演示目标数据形状，不是 M1 响应或已发生的游戏事件；使用现有内核信封。HP 片段仅在服务端已经确认该观察者可以看到精确 HP 时发送，不能把可见性留给客户端自行过滤。

世界适配器把 `melee_attack + spear.melee + hit` 绑定到前摇/出手/命中点/受击/飘字；正式动画没有安装时，使用同一绑定的几何占位动作。11→7 来自权威事件而非播放器的减法规则。播放结束只清理表现队列，不请求第二次扣血或补发奖励。`caused_by` 指向同一动作轨迹中的前序事件，完整轨迹验收要核对该引用存在和顺序。

### 资源映射与无素材验收

世界 manifest 声明稳定 asset_key，以及坐标尺度、实体外形类别、表现协议版本和支持的语义名称。具体 Web/Godot 客户端的绑定表再提供本地动画片段、骨骼/挂点、音效、投射物、UI 图标、比例与必要的播放参数。资源定位复用已有 asset/https 引用；下载的内容是数据，不执行世界作者任意脚本。

没有素材时显式采用几何占位包；语义缺失/版本不支持须报告，不能偷偷漏掉关键行为。一个美术包切换为另一个包后，同一事件轨迹与最终状态应一致。不是承诺任意模型/骨骼无需适配：坐标、朝向、尺寸、挂点和动画语义仍必须在绑定表里对齐。

快照恢复需拿到同一观察范围的流锚点并衔接增量，优先使用底座现有视图+流能力，不继续并排轮询两个无关联结果来拼出一次攻击。权限收紧时不只是隐藏 UI，还要清理缓存和旧事件。历史事件只展示当时已授予的视图，不借公共资源表泄露未探索房间或隐身实体。

## 9. 基础设施准备情况与补齐标准

| 需求 | 已有能力 | 本世界/后续待做 |
|---|---|---|
| 状态与事件/奖励同事务 | FunctionContext、FunctionOutcome、版本化状态与回执 | 世界定义战役/角色/奖励 schema 和唯一领取来源 |
| 随机结果不重复结算 | ctx.random_int 与操作回执 | SRD 规则和非法动作先验证，不另建 RNG 服务 |
| 待决/恢复 | 可持久化状态、定时器、活动与同身份认证 | 世界保存规则继续点；不用进程内 sleep 保存战斗 |
| 快照+增量+历史 | ViewSpec、StreamSpec、流锚点和保留、EventLedger | 新前端真正接入；检查因果次序和隐私投影 |
| 语义表现+资源 | PresentationCue、资源引用、已有队列 | 世界 payload/schema、资源绑定表和占位播放器；通用校验/播放原语确需时可补可选库 |
| 私密可见性 | 认证视图/流和按角色的 EventSpec | 先一场冒险、明确参与者，避免把全局公开流当多战役私信；客户端过滤不算授权 |
| 开发者接入 | 现有 WorldDefinition/FunctionSpec 和传输 | 文档、可运行世界模板、边界说明和复用实例；不冻结“零二开”承诺 |

已有数据结构允许做某事，不等于工具链已经好用。只有新世界能通过公开接口完成注册、启动、读取、执行、恢复和占位表现，并知道哪些地方需要编写适配器，才称得上基础设施交付。

## 10. 真游戏验收门槛

1. 一个用户无第二个敌方账号也能开始、完成和再次进入同一冒险。
2. 从营地到探索、战斗/替代解决、奖励、返回、升级、使用新能力的完整链路可跑；不直接在数据库塞满级角色冒充成长。
3. 经验、装备、目标与战利品刷新/重启/换客户端后仍一致；用不同操作 ID 也不能重复领奖。
4. 面向玩家看到的是角色位置、动作、风险和结果；不是只能读 JSON 或一排后台字段。
5. 无正式素材时，移动、攻击、命中/未命中、受击、倒地、拾取、升级和状态增减已有连续且因果正确的占位反馈。
6. 同一真实事件记录替换两套占位皮肤，状态/事件事实不变；缺少必要资源绑定会被发现。
7. 在移动/反应/领奖/升级选择中断开并恢复，不重复扣资源、不偷偷替用户放弃，也不重播历史当现场。
8. 死亡、撤退、放弃任务和完成目标有明确且可持续保存的结果；不能仅有胜利路径。
9. 未探索区域、隐藏敌人和私有构筑不从公共快照、事件、discovery、资源目录或缓存中泄露。
10. 自动敌人遵守相同规则，固定随机源回归和服务器随机实例分开标注；没有把规则脚本说成模型自主性。
11. 单人/合作配置的收益、危险与资源曲线分别测量；没有声称一个 XP 预算等同于已完成平衡。
12. 每个新公开动作能追到规则/作者裁定、调用 schema、事实变化、表现反馈和验收用例；没有只测试 API 成功。

## 11. 继续开发的顺序

先做 G1：六区域、一个合法角色的 1→2 级完整冒险 + 全链路占位表现。需要的基础设施边做边按通用性补齐，不先做一个巨大通用 RPG SDK。

再做 G2：三职业 1→3 级的合法构筑、相关法术/状态/休息规则闭包和合作验收。

再做 G3：8–12 区域完整序章、多路线奖励预算、终局、隐私投影和资源替换验收。

最后用实际可用的强模型做少量 canary 和双世界回归。正常身份/事务正确性保留；FreeAPI 专用网络补丁、无限重试、庞大模型矩阵不进入本计划。更可靠的模型减少模型故障，但不替代游戏规则和可见反馈。
